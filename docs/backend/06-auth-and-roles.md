# Авторизация и роли

Назад к плану: [`README.md`](README.md). Экран входа — [`../admin/design/13-login.md`](../admin/design/13-login.md).

## 1. Схема

- Логин по email и паролю, Spring Security, форма входа своя (SPA), API — `POST /api/auth/login`.
- Сессия на сервере, хранится в PostgreSQL через Spring Session JDBC. Поэтому деплой и перезапуск не разлогинивают пользователей.
- Cookie `SESSION`: `HttpOnly`, `Secure`, `SameSite=Lax`, путь `/`. Флаги заданы в `SecurityConfig`; `Secure` выключается только в профиле `local` (там `http://localhost`).
- Таймаут неактивности — 12 часов (`server.servlet.session.timeout`). Срок жизни сессии ограничен 7 днями от создания (`SessionPolicyFilter`): дальше `401 SESSION_EXPIRED` и вход заново.
- После входа ID сессии меняется (защита от session fixation), CSRF-токен тоже выдаётся новый.
- CSRF-защита включена: `csrf().spa()` с `CookieCsrfTokenRepository` + заголовок `X-XSRF-TOKEN` ([`05-api.md`](05-api.md) §4).
- Отключение пользователя, смена его роли и сброс пароля удаляют все его сессии (строки `spring_session` по `principal_name`). Смена своего пароля завершает остальные сессии, текущая остаётся.
- Пока у пользователя временный пароль (`must_change_password`), API отвечает `403 PASSWORD_CHANGE_REQUIRED` на всё, кроме `/api/auth/**`.

## 2. Пароли

- Хеш: `DelegatingPasswordEncoder` Spring Security (по умолчанию bcrypt). Префикс алгоритма в хеше позволяет позже сменить алгоритм без массового сброса паролей.
- Длина от 12 до 128 символов; проверка по списку частых паролей (`auth/common-passwords.txt`); не меньше 4 разных символов; пароль не должен содержать имя из email.
- Временный пароль — 16 случайных символов (`SecureRandom`, без похожих `0/O`, `1/l/I`).
- Восстановления по почте в MVP нет. Пароль менеджера сбрасывает владелец: генерируется временный, при входе обязательна смена (`must_change_password`). Пароль владельца сбрасывается командой на сервере (§4).

## 3. Роли

Две роли; владелец подтвердил 22.10.2026 ([`README.md`](README.md) §6, вопрос 3). Владелец не может сменить роль себе или отключить себя, и в системе всегда остаётся хотя бы один активный владелец.

| Действие | Власник (`OWNER`) | Менеджер (`MANAGER`) |
| --- | --- | --- |
| Заказы: смотреть, создавать ручные, подтверждать, отменять, вводить ТТН | да | да |
| Товары, категории, бренды: смотреть и редактировать | да | да |
| Остатки: ручная правка | да | да |
| Правила цен | да | только смотреть |
| Інтеграції: смотреть статус, повторить ошибки | да | да |
| Інтеграції: сменить режим записи, ключи площадок, запустить джобу | да | нет |
| Пользователи: создать, отключить, сбросить пароль | да | нет |
| Налаштування | да | только смотреть |

Проверка — аннотациями `@PreAuthorize` на сервисах, а не только скрытием кнопок в админке. Каждая строка матрицы покрыта тестом (шаг 6.2): строки «Пользователи» — уже, остальные — вместе с эндпоинтами этапа 7.

## 4. Первый владелец

В репозитории нет ни логинов, ни хешей — он публичный. Первый пользователь создаётся командой на сервере через Session Manager:

```bash
cd /opt/triomio
docker compose run --rm -it app create-owner --email owner@<domain> --name "Ім'я Прізвище"
```

Команда **спрашивает** временный пароль (дважды, без отображения), а не печатает его: всё, что пишет контейнер, уходит в CloudWatch. Без терминала пароль читается одной строкой из stdin. Пароль проверяется по тем же правилам (§2); при первом входе система требует его сменить. Та же команда с `--reset` задаёт новый временный пароль существующему владельцу, снова включает его и завершает его сессии.

Локально демо-пользователи `owner@demo.local` и `manager@demo.local` создаются в профиле `local`, если в `backend/.env.local` задан `app.demo.user-password` (12+ символов). В репозитории этого пароля нет.

## 5. Защита от перебора

- Не больше 5 неудачных попыток за 15 минут для пары «email + IP» (таблица `login_attempts`). Дальше — `429 TOO_MANY_ATTEMPTS`, пока самая старая из этих попыток не выйдет из окна. Успешный вход обнуляет счётчик.
- Ответ на неверный email, неверный пароль и отключённую учётку одинаковый, по тексту и по времени: для неизвестного email всё равно проверяется bcrypt-хеш (подставной).
- Все входы, неудачные попытки, блокировки, смены паролей, ролей и активности пишутся в `audit_log` (`entity_type = USER`, `kind = USERS`).
- Реальный IP клиента приходит от nginx в `X-Forwarded-For` (`server.forward-headers-strategy: native` в профиле `prod`). nginx на хосте ходит в `127.0.0.1:8080`, поэтому внутри контейнера запрос приходит с адреса шлюза Docker-сети. Tomcat по умолчанию доверяет заголовку только от частных подсетей (`10/8`, `172.16/12`, `192.168/16`, `127/8`), куда входит и сеть Docker; снаружи порт 8080 закрыт.
- Старые строки `login_attempts` чистит джоба очистки (этап с Quartz-джобами); просроченные сессии Spring Session удаляет сам раз в 15 минут.

## 6. Что не входит в MVP

- Двухфакторная аутентификация для пользователей CRM (кандидат на добавление сразу после запуска — для владельца).
- Вход через Google и SSO.
- Учётки покупателей сайта — отдельная тема вместе с сайтом.
