# Синхронизация с площадками: безопасный контур

Назад к плану: [`README.md`](README.md).

Этот документ — техническое исполнение [`../integrations/LIVE-ACCOUNTS-SAFETY.md`](../integrations/LIVE-ACCOUNTS-SAFETY.md). Если они в чём-то расходятся, прав `LIVE-ACCOUNTS-SAFETY.md`, а этот документ нужно исправить. Бизнес-логика синхронизации (остатки, цены, категории) — [`../integrations/README.md`](../integrations/README.md); контракты API — [`prom-api.md`](../integrations/prom-api.md), [`rozetka-api.md`](../integrations/rozetka-api.md), [`epicentr-api.md`](../integrations/epicentr-api.md).

## 1. Принцип

Любой изменяющий вызов к площадке проходит три проверки, и каждая может его остановить:

1. **Режим площадки** в базе (меняет владелец в админке).
2. **Потолок режима** из переменной окружения на сервере (меняется только через `.env` и перезапуск).
3. **Предохранители** в outbox-диспетчере (массовое обнуление, резкое изменение цены, демо-товары).

## 2. Режимы

| Режим | Чтение (заказы, справочники, сверка) | Запись (цена, остаток, статус заказа) |
| --- | --- | --- |
| `OFF` | нет | нет; строки outbox → `BLOCKED` |
| `READ_ONLY` | да | нет; строки outbox → `BLOCKED` |
| `DRY_RUN` | да | тело запроса собирается и сохраняется, HTTP-вызова нет; строки → `DRY_RUN` |
| `LIVE` | да | да |

- По умолчанию у каждой площадки `READ_ONLY`, локально — `OFF`.
- Действующий режим = минимум из режима в базе и `INTEGRATIONS_MAX_MODE` из env. На сервере потолок по умолчанию `DRY_RUN`. Поднять его до `LIVE` — отдельное явное решение владельца, изменение `.env` и перезапуск.
- Сменить режим в админке может только `OWNER`. Перед переходом в `LIVE` — диалог подтверждения с названием площадки; переход пишется в `audit_log`.
- Одно действие «Вимкнути запис» (переход в `READ_ONLY`) доступно на странице «Інтеграції» и описано в [`ops/06-incidents.md`](ops/06-incidents.md).

## 3. Outbox

Изменение в CRM и строка «что отправить» пишутся в одной транзакции (transactional outbox). Отдельная джоба отправляет ([`07-jobs-quartz.md`](07-jobs-quartz.md) §3).

- **Только абсолютные значения.** Остаток = текущее `available`, цена = результат правила. Повторная отправка не задваивает списание ([`../integrations/README.md`](../integrations/README.md), «Схема синхронизации»).
- **Схлопывание.** `dedupe_key = marketplace:kind:product_id`. Пока строка `PENDING`, новое изменение того же товара обновляет её payload, а не создаёт новую.
- **Повторы.** Ошибки сети, `5xx` и `429` → повтор с задержкой 30 с, 2 мин, 10 мин, 30 мин, затем раз в час. После 10 попыток → `FAILED` и алерт. `4xx` кроме `429` → сразу `FAILED`: повтор не поможет.
- **Пачки.** Если у площадки есть массовый метод (Rozetka `PUT /items/mass-update`, Prom `POST /products/edit_by_external_id`), диспетчер собирает до 50 товаров одной площадки в один запрос.

## 4. Предохранители

| Предохранитель | Срабатывает | Действие |
| --- | --- | --- |
| Массовое обнуление | за 10 минут больше 10 SKU или больше 20 % активного каталога площадки должны уйти в 0 / `out_of_stock` | площадка → `READ_ONLY` с причиной в `paused_reason`, алерт, строки остаются `PENDING` до решения человека |
| Резкое изменение цены | новая цена выше старой в 1,5 раза или ниже в 2 раза (строже порога Rozetka, [`../integrations/README.md`](../integrations/README.md), «Резкое изменение цены») | строка → `BLOCKED`, требуется подтверждение владельца в админке |
| Демо-товар | `is_demo = true` | строка не создаётся вообще; фид такой товар не включает |
| Товар не готов | `DRAFT`/`ARCHIVE`, канал выключен или не заполнены обязательные поля | строка не создаётся |
| Изменение статуса заказа | любой переход статуса заказа на площадке | только по действию пользователя в карточке заказа; никаких автоматических подтверждений и отмен в MVP |

Пороговые значения лежат в `settings` и меняются владельцем.

## 5. Ключи площадок

- Ключ вводит владелец в «Інтеграціях» (`PUT /api/integrations/{marketplace}/credentials`). Ни в репозитории, ни в `.env` ключей площадок нет.
- В базе ключ хранится зашифрованным AES-256-GCM. Мастер-ключ — в SSM Parameter Store (`/triomio/prod/crypto/master-key`) и попадает в приложение через `.env` на сервере. Без мастер-ключа дамп базы бесполезен для атакующего.
- API возвращает только маску (`••••1a2b`) и дату изменения.
- HTTP-клиенты не логируют заголовок `Authorization` и тело запросов с токенами; `sync_log` хранит только выдержки без них.
- Замена ключа: новый ключ в кабинете площадки → сохранить в CRM → отозвать старый в кабинете.

## 6. HTTP-клиенты

- Отдельный `RestClient` на площадку: таймаут соединения 5 с, чтения 30 с.
- Rate limiter Resilience4j: по умолчанию 2 запроса в секунду на площадку. Официальных лимитов площадки не публикуют; поднимаем, только если упираемся.
- Повтор на уровне клиента — только для чтения (`GET`). Запись повторяет outbox по своим правилам.
- Каждый вызов → строка в `sync_log` (метод, путь, статус, длительность).
- Все статусы и коды площадок маппятся в наши явными таблицами; неизвестный статус → алерт, а не угадывание ([`../integrations/LIVE-ACCOUNTS-SAFETY.md`](../integrations/LIVE-ACCOUNTS-SAFETY.md) п. 10).

## 7. Порядок включения площадки

Каждый шаг — после явного «да» владельца в чате. Это детализация этапа 10 в [`README.md`](README.md).

| Шаг | Режим | Где | Как понять, что можно дальше |
| --- | --- | --- | --- |
| 1 | `READ_ONLY` | с EC2 один безопасный `GET` | ответ не 403 и не таймаут: IP AWS не заблокирован |
| 2 | `READ_ONLY` | тестовая компания Prom | заказы появляются в CRM, в `sync_log` нет изменяющих запросов |
| 3 | `LIVE` | тестовая компания Prom, тестовый товар | цена и остаток доходят, сверка без расхождений |
| 4 | `READ_ONLY` | боевой кабинет | заказы приходят, статусы маппятся без «неизвестных» |
| 5 | `DRY_RUN` | боевой кабинет, неделя | владелец просмотрел отчёт `dry-run-report` |
| 6 | `LIVE`, один SKU | боевой кабинет | сутки без расхождений |
| 7 | `LIVE`, весь каталог | боевой кабинет | сутки без расхождений, алертов нет |
| 8 | URL фида в кабинете | боевой кабинет | без опций «отсутствующие в файле → …» |

У Rozetka и Epicentr нет тестового контура ([`../integrations/LIVE-ACCOUNTS-SAFETY.md`](../integrations/LIVE-ACCOUNTS-SAFETY.md), «Песочницы»), поэтому шаги 2–3 для них пропускаются, а шаг 5 обязателен и длится не меньше недели.
