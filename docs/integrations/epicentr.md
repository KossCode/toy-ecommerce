# Интеграция с маркетплейсом «Епіцентр» (epicentrk.ua)

Исследование для «Лапки»: сайт — единственный источник правды о товарах, Epicentr — один из трёх каналов (вместе с Rozetka и Prom). Дата исследования: 7 октября 2026.

Обозначения:

- **[Док]** — подтверждено официальной документацией (база знаний `supportm.epicentrk.ua` или OpenAPI-спецификация Merchant API). Ссылка на источник стоит рядом.
- **[Вывод]** — наш вывод из документации или из стороннего источника. Нужна проверка на реальном аккаунте.
- **[Нет данных]** — в документации не нашли.

Номера источников вида [S1] расшифрованы в конце документа.

## 1. Кратко

1. **Каталог передаётся XML-фидом в формате YML** (`<yml_catalog>` → `<offers>` → `<offer>`). Категории, наборы атрибутов, характеристики и значения задаются **числовыми или хэш-кодами Epicentr**, которые берутся из справочников Merchant API (`/v2/pim/...`). Названия и описания передаются на двух языках (`lang="ua"` / `lang="ru"`). [Док, S1]
2. **Полный фид не перечитывается автоматически.** Импорт со всеми полями («Оновити все») запускается вручную в кабинете: загрузкой файла или указанием ссылки. Автоматически по ссылке работает только **«Автооновлення залишків»**: оно обновляет цену, старую цену и наличие. По умолчанию это происходит **раз в сутки в 24:00 UTC**. Через менеджера или поддержку можно включить интервал 12 ч, 4 ч или 1 ч. [Док, S2, S5]
3. **Количество остатка Epicentr не принимает нигде.** Ни в фиде, ни в API нет поля «количество», есть только статус: `in_stock`, `under_the_order` или `out_of_stock` (в API — `not_available`). Поэтому после продажи Epicentr **сам ничего не списывает** и не снимает товар с продажи. Это делаем мы, присылая новый статус. [Док, S1, S2, S8; вывод об отсутствии авто-списания — Вывод]
4. **Seller API (Merchant API) есть**: REST, `https://merchant-api.epicentrm.com.ua`, авторизация `Authorization: Bearer <token>`. Он покрывает полный цикл заказов: список с курсорной пагинацией и фильтром по `updatedAt`, детали, допустимые статусы, смену статуса, ТТН, состав заказа, комментарии. Есть **пакетное обновление цены и наличия** `POST /v1/offers` (до 1000 позиций, результат асинхронный). Справочники категорий и атрибутов тоже в API. [Док, S8]
   - Оговорка: спецификация помечена как «closed beta-test for a limited amount of companies». FAQ базы знаний до сих пор пишет «API доступне лише для обробки замовлень, обміну цін та залишків немає», то есть `POST /v1/offers` может быть закрыт для конкретного аккаунта и требует отдельного права. [Док, S3, S8]
5. **Webhooks нет, лимиты запросов не опубликованы, тестовой среды нет.** О новых заказах узнаём опросом (polling). Все вызовы сразу работают на проде. [Док, S3; про webhooks и лимиты — Нет данных, S8]
6. **Создать или изменить карточку через API нельзя.** Из PIM в спецификации есть только справочники. Модерация, статусы карточек и отчёты об ошибках импорта доступны только в кабинете. Название, бренд, категорию, набор атрибутов и артикул опубликованного товара меняет только категорийный менеджер. Варианты («різновиди») создаются только вручную в кабинете. [Док, S6, S9, S8]

**Рекомендуемая схема синхронизации:** опрашивать `GET /v4/oms/orders` каждые 1–2 минуты. По новым и изменённым заказам списывать остаток на сайте, а пересчитанный статус наличия рассылать на все площадки. В Epicentr — через `POST /v1/offers`, если метод открыт, а запасным путём — через «Автооновлення» с интервалом 1 час. Подробно в разделе 5.

## 2. Формат товарного фида (экспорт с сайта в Epicentr)

### 2.1. Общая структура [Док, S1]

```xml
<?xml version="1.0" encoding="UTF-8"?>
<yml_catalog date="2026-10-07 21:00">
  <offers>
    <offer id="..." available="true|false">
      ...
    </offer>
  </offers>
</yml_catalog>
```

- `yml_catalog@date`: дата генерации в формате `рік-місяць-день години:хвилини`. В примере документации значение стоит в фигурных скобках (`date="{2020-11-09 15:15}"`). Скорее всего, это опечатка шаблона. [Док, S1; про скобки — Вывод]
- В отличие от классического YML для Prom и Rozetka, **нет блоков `<shop>`, `<currencies>`, `<categories>`**: категория указывается прямо в оффере кодом Epicentr. [Док, S1]

### 2.2. Поля оффера

| Элемент / атрибут | Обязательность | Тип и ограничения | Комментарий | Источник |
| --- | --- | --- | --- | --- |
| `offer@id` | Обязателен | string, до 64 символов, «цифрове або буквено-цифрове значення **без розділових знаків**» | Это «Артикул» в кабинете, по нему работают обновление и автообновление. Статья про XLSX рекомендует числовой артикул до 25 символов. | S1, S2, S4 |
| `offer@available` | Обязателен | boolean `true`/`false` | Используется, если нет `<availability>` | S1 |
| `<price>` | Обязателен | float, гривны, разделитель — точка (`25.78`) | Без букв и валюты | S1, S2 |
| `<price_old>` | Опционален | float | Цена до скидки. Должна быть **больше** `<price>`, иначе товар не опубликуют. Если скидки нет, тег удаляется. | S1, S4 |
| `<availability>` | Опционален | `in_stock`, `under_the_order`, `out_of_stock` | Приоритетнее `available`. Только через этот тег можно поставить «Під замовлення». | S1, S2, S5 |
| `<category code="...">Назва</category>` | Обязателен для нового товара | `code` — числовой код **конечной** категории (`hasChild=false`), текст — название UA или RU | Коды из `GET /v2/pim/categories?filter[hasChild]=false` | S1, S8 |
| `<attribute_set code="...">Назва</attribute_set>` | Обязателен для товара с характеристиками | `code` из `attributeSets[].code` категории | Определяет, какие характеристики есть и какие обязательны | S1, S8 |
| `<picture>` | Обязателен (без фото товар не создаётся) | URL. Несколько фото — **в одном теге через запятую и пробел**. Первое фото — главное. | Требования к фото — в разделе 2.5 | S1, S4 |
| `<name lang="ua">` | Обязателен | string, до 150 символов. Формат: `[категорія] + [особливість] + [бренд] + [модель] + [інше]` | | S1 |
| `<name lang="ru">` | Опционален | то же | Нужен, только если товар должен показываться на русской версии сайта | S1 |
| `<description lang="ua">` / `lang="ru"` | Желателен | до 12 160 символов, HTML в `<![CDATA[...]]>`. Разрешены только `<p> <br> <b> <ul> <li> <table> <tr> <td>`, остальные теги вырезаются. | | S1 |
| `<param paramcode="..." name="..." [valuecode="..."] [lang="..."]>` | По набору атрибутов | Типы: text (1–12 160), string (1–256), float/int (±9 999 999), select, multiselect | Подробности в разделе 2.3 | S1 |

### 2.3. Характеристики (`<param>`) [Док, S1]

- **Текстовые** (например, комплектация): значение в `CDATA`, по одному `<param>` на язык с `lang="ua"` и `lang="ru"`. `paramcode` в обоих одинаковый.
- **Select**: `paramcode` + `valuecode` (код значения из `GET /v2/pim/attribute-sets/{attributeSetCode}/attributes/{attributeCode}/options`), текст — название значения.
- **Multiselect**: `valuecode="код1,код2"`, текст `"назва1, назва2"`.
- **Числовые габариты**: `width`, `height`, `length` в **мм**, `weight` в **г**, значение в `CDATA`, только цифры.
- Служебные `paramcode` из шаблона: `brand` (select, значение из справочника брендов Epicentr), `country_of_origin` (например, `valuecode="chn"`), `measure` (`measure_pcs` = «шт.»), `ratio` (минимальная кратность), `barcodes` (штрихкод).
- `name` у `<param>` можно писать на любом языке, сопоставление идёт по коду.

**Бренд.** Если бренда нет в справочнике Epicentr, его заранее добавляет категорийный менеджер по письму продавца. [Док, S6]

### 2.4. Категории и наборы атрибутов

- У Epicentr собственное дерево категорий. Товар должен лежать в **открытой конечной** категории. [Док, S4, S6]
- Справочники (нужен токен) [Док, S1, S8]:
  - `GET /v2/pim/categories` (параметры `page`, `filter[hasChild]`): коды категорий, названия и привязанные `attributeSets[].code`;
  - `GET /v2/pim/attribute-sets` (`page`, `filter[codes][]`): атрибуты набора, их коды, типы и признак обязательности (`isRequired` есть в схеме `attributeSetSettings`);
  - `GET /v2/pim/attribute-sets/{attributeSetCode}/attributes/{attributeCode}/options`: допустимые значения select и multiselect.
- **Коды игрушечных категорий («Конструктори», «М'які іграшки» и т. д.) и их обязательные атрибуты без токена не получить**: эндпоинты отвечают `403`. Список ниже нужно выгрузить после получения доступа. [Нет данных]
- Возраст ребёнка, материал, количество деталей и т. п. в Epicentr — обычные `<param>` из набора атрибутов категории. Конкретные `paramcode` неизвестны. [Вывод]

### 2.5. Изображения [Док, S1, S4]

- Минимум одно фото. Хорошее качество, белый или студийный фон.
- Минимальный размер: **600×500 px** по статье про XML и **500×500 px** по статье про XLSX. Ориентируемся на ≥ 600×500, лучше ≥ 1000×1000. [Док; выбор порога — Вывод]
- Главное фото: без водяных знаков, без посторонних предметов, товар занимает от 80 % кадра.
- Отдельная статья «Вимоги до візуального контенту» есть, но в рамках исследования не разбиралась [S10].

### 2.6. Варианты (цвет, размер)

- В фиде **нет** механизма группировки вариантов: ни `group_id`, ни аналога. «Створення різновидів товару доступно **виключно в Особистому кабінеті в ручному режимі**». Объединяются товары одной категории, которые отличаются хотя бы одной «модельной» характеристикой. [Док, S9]
- Для нас это значит: каждый вариант — отдельный `offer` со своим артикулом, а склейку делают руками в кабинете. [Вывод]

### 2.7. Лимиты

- XLSX-импорт: до 100 000 товаров в файле. Экспорт из грида: до 50 000. [Док, S4, S7]
- Лимит размера и числа товаров для XML **не указан**. [Нет данных]
- Пока импорт выполняется, повторно запустить его нельзя. [Док, S6]

### 2.10. Совместимость с фидом Prom

В кабинете есть отдельный импорт **«Імпорт з інших майданчиків»**: ссылка на YML-экспорт Prom. Обязательные поля: `price`, `name`, `categoryId`, `offer`. При этом категории **не сопоставляются**: после импорта карточки создаются в статусе «Чернетка» без категории, характеристики дозаполняются вручную или XLSX-файлом. [Док, S11]

Вывод: для первичного заведения можно скормить Epicentr тот же фид, что для Prom. Для полноценной публикации без ручной работы нужен отдельный фид в формате Epicentr с кодами. Тот же URL можно потом использовать для автообновления цены и наличия. [Вывод]

## 3. Как Epicentr получает данные и как часто

| Механизм | Что обновляет | Как запускается | Частота и задержка | Источник |
| --- | --- | --- | --- | --- |
| Импорт «Оновити все» (файл или ссылка) | Создаёт новые товары и обновляет всё, включая характеристики | **Вручную в кабинете**: «Товари → Імпорт», способ «Файл» или «посилання на файл», кнопка «Імпортувати» | Разово. После импорта — отчёт. Изменения опубликованных карточек уходят на перемодерацию. | S1, S5, S6 |
| Импорт «Оновити тільки ціну та наявність» (файл или ссылка) | Цена, старая цена, наличие. Новые товары не создаёт. | Вручную в кабинете | Наличие на сайте меняется в течение ~30 минут, без перемодерации | S5, S7 |
| **«Автооновлення залишків»** (ссылка на XML) | Цена, старая цена, наличие. Ищет товары по артикулу (`offer id` = «Артикул»). | Ссылка сохраняется один раз, дальше Epicentr сам скачивает файл | **По умолчанию 1 раз в сутки в 24:00 UTC.** Через менеджера или поддержку: раз в 12 ч, 4 ч или 1 ч. | S2 |
| Опция «Змінити статус товарів, яких немає у файлі, на "Немає у наявності"» | Снимает с наличия товары, пропавшие из файла | Галочка в настройках автообновления | Вместе с автообновлением | S2 |
| **API `POST /v1/offers`** | Цена, старая цена, наличие. До 1000 позиций за запрос, по `sku` или `productId`. | Из нашего бэкенда | Асинхронно: ответ `201` с `requestId`, статус через `GET /v1/offers/update-results/{requestId}`. Скорость применения не указана. | S8 |
| Ручное редактирование в кабинете или XLSX из грида | Любые поля, в зависимости от статуса карточки | Вручную | — | S6, S7 |

- **Запустить автообновление вне расписания через API нельзя.** Похоже, нельзя и в кабинете: такой кнопки в документации нет. Срочное обновление — только ручным импортом «Оновити тільки ціну та наявність» или через `POST /v1/offers`. [Вывод; в документации нет данных о кнопке «обновить сейчас»]
- Изменение контента опубликованного товара (описание, фото, характеристики): перемодерация, на сайте — **на следующий день** после подтверждения. Если меняются только числовые характеристики, подтверждение автоматическое. [Док, S6]

## 4. Merchant API

### 4.1. Общее [Док, S3, S8]

- Swagger UI: `https://merchant-api.epicentrm.com.ua/swagger/`. Спецификации: `swagger.yaml` (EN) и `swagger.ukr.yaml` (UA), OpenAPI 3.0, версия 1.0.0.
- Базовый хост: `https://merchant-api.epicentrm.com.ua`. Он же указан в примерах базы знаний и GitHub. В описании спецификации встречается `mp-api.epicentrm.com.ua`, но этот хост сейчас не резолвится. [Док + проверка]
- Авторизация: заголовок `Authorization: Bearer mp_<token>`. В спецификации заявлены также `jwt` и `wsse` (`X-WSSE`), для продавца используется токен из кабинета.
  - Токен генерирует роль **«Адміністратор компанії»**: сначала включить тогл в «Додаткові налаштування», затем «Налаштування → Налаштування компанії → API». Вкладку открывает куратор (категорийный менеджер).
  - Токены бессрочные, их может быть несколько, отзываются удалением.
- Все даты в **UTC**. Все действия логируются.
- **Тестовой среды нет**: изменения через API сразу видны в кабинете.
- **Webhooks**: в спецификации нет ни одного упоминания webhook или callback. [Нет данных → считаем, что их нет]
- **Rate limits**: не описаны, кода `429` в спецификации нет. [Нет данных]
- Статус документа: «closed beta-test for a limited amount of companies». Отзывы присылать на `merchant@epicentrk.ua`.
- Официальные примеры (Python, Node.js, PHP, Java) лежат в `github.com/epicentrm/merchant-api`. Там тривиальный `GET /v1/my/user`, которого в текущей спецификации нет.

Без токена эндпоинты отвечают `403`: проверено на `/v2/pim/categories` и `/v4/oms/orders`.

### 4.3. Модель заказа (важное для синхронизации) [Док, S8]

- `id` (uuid, это `orderId`), `number` (номер для людей), `statusCode`, `createdAt`, `updatedAt`, `subtotal`, `payed`, `hasPreOrderItems`, `externalId`.
- `items[]`: `offerId` (uuid), `productId`, **`sku`** и `productExternalId` (наш артикул), `title`, `price`, `quantity`, `subtotal`, `measure`, `ratio`, вложенный `product` со `statusCode` карточки (`draft`, `moderating`, `published`, `banned`, `rework`, `new`, `enrich`).
- Статусы заказа: `new`, `confirmed_by_merchant`, `confirmed`, `sent`, `received`, `delivered`, `completed`, `closed`, `canceled`, `returned`, `return_requested`, `canceled_by_merchant`, `completed_merchant_rejection`, `closed_merchant_rejection`.

## 5. Заказы и синхронизация остатков

### 5.1. Правила обработки заказа на Epicentr [Док, S3, S12, S13, S14]

- Новый заказ (`new`) нужно подтвердить (`confirmed_by_merchant`) или отменить **в течение 120 минут**. Если не успеть, Epicentr напомнит, через 60 минут отменит заказ сам и **может заблокировать компанию**.
- Рабочее время по умолчанию — пн–пт 9:00–18:00. Заказы, пришедшие в нерабочее время, обрабатываются до 11:00 следующего рабочего дня.
- **Данные покупателя видны только после перевода в `confirmed_by_merchant`.**
- Цепочка: `new` → `confirmed_by_merchant` → (звонок покупателю) → `confirmed` → `sent` (с ТТН) → `delivered` → `completed` → через 14 дней `closed` (списание комиссии).
- Если заказ провёл 21 день в промежуточном статусе, он автоматически становится `completed`. На оспаривание есть 5 дней.
- Отмена из `new` — без комиссии. Отмена после подтверждения по вине продавца — с комиссией. Через API нужно передать причину (`translationKey`, например `order.cancel_reason.product_not_available`).
- Права роли: «Суперадмін компанії» может отменять заказы из `new`, `confirmed_by_merchant`, `confirmed`, `sent`, `delivered`, а «Адміністратор компанії» — только из `new` (так в кабинете; насколько это распространяется на API-токен, не указано). [Док, S14; применимость к API — Нет данных]
- Возврат (`return_requested` → `returned`) в итоге оформляет поддержка Epicentr.

### 5.2. Что происходит с остатком на Epicentr после продажи

- Количества у Epicentr нет, только статус наличия [S1, S2, S8]. **[Вывод]** Значит, продажа на Epicentr не меняет статус оффера: товар остаётся `in_stock`, пока мы не пришлём другой статус. Риск — оверселл последней единицы. Явного утверждения об этом в документации нет.
- В обратную сторону то же самое: если последняя единица ушла на Rozetka, Epicentr узнает об этом только из нашего обновления.

### 5.3. Рекомендуемая схема

1. **Сайт хранит числовой остаток** и сам вычисляет статус для каждой площадки (`in_stock` при остатке > 0 или > резерва безопасности, иначе `out_of_stock`).
2. **Приём заказов Epicentr** — воркер каждые 1–2 минуты:
   - `GET /v4/oms/orders?filter[updatedAt][from]=<последняя отметка>&sort[]=updatedAt&limit=…` с курсором. В примерах фильтр `updatedAt` задан датой (`2020-10-09`), поэтому дополнительно дедуплицируем по `id` и `updatedAt` у себя. [Док; про гранулярность фильтра — Вывод]
   - Для новых заказов вызываем `GET /v6/oms/orders/{id}` и сопоставляем `items[].sku` с нашим SKU.
   - **Резервируем или списываем остаток в момент появления `new`**, а не при подтверждении: у конкурирующих площадок окно до подтверждения — 2 часа. При `canceled`, `canceled_by_merchant` или `returned` возвращаем остаток.
3. **Распространение изменений.** После любого изменения остатка (продажа на любой площадке, приход, ручная правка в админке) ставим SKU в очередь. Отдельный воркер раз в 30–60 секунд отправляет пачку в `POST /v1/offers` (до 1000 позиций) по полю `sku`, затем опрашивает `update-results/{requestId}` и пишет результат в журнал синхронизации админки.
4. **Страховочный канал.** Постоянный URL короткого фида (цена и наличие по всем SKU) подключаем в «Автооновлення залишків» с интервалом 1 час (интервал включает менеджер) и опцией «товары, которых нет в файле → Немає в наявності». Если `POST /v1/offers` закрыт для аккаунта, это **единственный автоматический канал**. Тогда задержка до часа, и нужен резерв безопасности (например, выставлять `out_of_stock` на Epicentr при остатке ≤ 1–2).
5. **Подтверждение заказа из админки** через `change-status/to/confirmed_by_merchant`, отмена — с причиной. Ссылка на заказ в кабинете: `https://admin.epicentrm.com.ua/oms/orders/{orderId}` [S3].
6. **Контент** (новые товары, правки описаний и характеристик) идёт отдельным полным фидом. Его импорт запускается **вручную в кабинете** при заведении новых позиций (см. раздел 6).

## 7. Открытые вопросы к владельцу бизнеса и менеджеру Epicentr

1. **Открыт ли для нашего аккаунта `POST /v1/offers`** (право «update offers»)? От этого зависит, обновляется наличие за секунды или раз в час.
2. Можно ли сразу включить **интервал автообновления 1 час**? Есть ли условия (рейтинг, объём)?
3. **Формат артикула**: примет ли Epicentr `LP-10018` с дефисом или переходим на `LP10018`? Решить до первого импорта: после публикации артикул меняет только менеджер.
4. Есть ли **лимиты частоты запросов** к Merchant API? Сколько времени проходит от `enqueued` до `processed` и до витрины?
5. Есть ли планы на **webhooks о новых заказах** или нужно опрашивать каждую минуту?
6. **Коды категорий и наборов атрибутов** для наших 8–10 категорий игрушек, список обязательных атрибутов (возраст, материал, пол и т. д.). Нужен токен, чтобы выгрузить их через `/v2/pim/*`.
7. Есть ли в справочнике брендов **LEGO, Hot Wheels, Barbie, Cubika, Тигрес, Viga Toys**? Что указывать у товаров без бренда?
8. Нужна ли **русская версия** названий и описаний или просим отключить RU?
9. Кто и в какие часы подтверждает заказы (SLA — 2 часа)? Делаем ли автоподтверждение из админки, если товар есть на складе?
10. Как мапим «Очікується»: в `out_of_stock` (рекомендуем) или в `under_the_order` с учётом правил «под заказ» (до 21 дня, без правила отправки за 2 дня)?
11. Нужен ли резерв безопасности (показывать «нет в наличии» при остатке ≤ N), пока задержка Epicentr неизвестна?
12. Какая роль у владельца токена: «Суперадмін» или «Адміністратор»? Распространяются ли ограничения роли на отмену через API?
