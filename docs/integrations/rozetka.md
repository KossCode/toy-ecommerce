# Интеграция с Rozetka Маркетплейс

Исследование для «Trio Mio»: как сайт, будучи единственным источником правды о товарах, выгружает каталог на Rozetka, забирает заказы и держит остатки в синхроне с Epicentr и Prom.

Дата исследования: 07.10.2026. Страницы справки продавца на момент чтения помечены «Останнє оновлення: 12.06.2026» (требования к XML — 29.06.2026, API — 26.08.2026). Спецификация API взята из публичного `api_data.json` документации apiDoc (сгенерирована 07.10.2026).

Обозначения:

- **[Док]** — подтверждено официальной документацией (ссылка в конце раздела или в «Источниках»).
- **[Вывод]** — наш вывод из документации, прямо не сказано.
- **[Не подтв.]** — встречается только у третьих лиц или не найдено; требует проверки на живом кабинете.

## 1. Summary

1. **Каталог** передаётся XML-фидом в формате YML (`yml_catalog` → `shop` → `categories` / `offers`), только UTF-8. Rozetka сама забирает его по статическому URL. **[Док]**
2. **Частота:** стандартная автосинхронизация с фидом — раз в час. Ручная синхронизация есть только кнопкой в кабинете, не чаще раза в 3 часа. Эндпоинта «пересчитать фид сейчас» в API нет. **[Док]**
3. **Быстрый канал для цены и остатка** — Seller API `PUT /items/mass-update` (цена, старая цена, промо-цена, остаток, мин./макс. в корзине). Чтобы он работал как источник правды, у прайс-листа в кабинете переключается тип синхронизации на «Особистий кабінет (API)». После этого цену и остаток из XML Rozetka не берёт. **[Док]** / **[Вывод]** про «не берёт из XML» — см. §3.3.
4. **API есть, полноценное:** ~360 методов (заказы, статусы, товары, ошибки, модерация, категории и характеристики, ТТН, чаты, баланс). Авторизация: логин + пароль (Base64) → Bearer-токен. Токен деактивируется после 24 часов простоя; есть отдельные API-токены по ролям. **[Док]**
5. **Вебхуков в официальной документации нет.** Новые заказы получаем опросом `GET /orders/search`. Уведомления продавцу о новом заказе приходят только в Telegram, Viber/SMS или email. **[Док]** (отсутствие — по полному тексту спецификации.) Сторонний модуль Odoo заявляет «Webhook підтримку» — **[Не подтв.]**.
6. **Остатки на стороне Rozetka:** при оформлении заказа Rozetka сама вычитает количество из остатка, а при отмене возвращает. Но если остатки идут из XML, следующая синхронизация перезапишет их значением из фида. **[Док]**
7. **Rate limits не задокументированы.** **[Док]** (отсутствие.)
8. **Рекомендуемая схема:** XML-фид отвечает за контент. Цена и остаток идут через API (источник синхронизации «Особистий кабінет (API)»). Опрос заказов раз в 1–2 минуты. Сайт резервирует товар и пушит **абсолютные** остатки на все три маркетплейса.
9. **Только в кабинете или через поддержку:** подключение и замена URL фида, ручная синхронизация, смена типа синхронизации, подтверждение «аномальной цены», создание категорий и характеристик, группировка, разархивация и удаление товаров, валидатор фида. Подробно — в §6.

## 2. Формат товарного фида

### 2.1 Общие технические требования [Док]

| Требование | Значение |
| --- | --- |
| Формат | XML (YML), корень `<yml_catalog date="YYYY-MM-DD hh:mm">` |
| Кодировка | Только UTF-8 (валидатор рекомендует UTF-8 без BOM) |
| URL фида | Статичный, не меняется со временем |
| Запрещённые символы | ASCII 0–31, кроме 9, 10, 13 |
| Экранирование | `" & < > '` в значениях → XML-сущности; HTML в описании — внутри `<![CDATA[ ]]>` |
| URL товара | Закодирован по RFC-1738 |
| `offer id` | **Только `A–Z a–z 0–9`.** Без кириллицы, пробелов, **дефисов** и прочих символов. Менять после добавления на маркетплейс запрещено |
| `category id` | Произвольная нумерация, менять запрещено |
| Несколько фидов | Можно, но товары не должны повторяться между фидами. Рекомендуется один URL |

> **Важно для «Trio Mio»:** наш SKU `TM-10018` содержит дефис, а в `offer id` допустимы только латинские буквы и цифры. Предлагаем `offer id="TM10018"` и передавать исходный SKU в `<article>TM-10018</article>`. Артикул виден только в кабинете и используется для поиска, в том числе в API (`article` в `GET /goods/all`). Правило преобразования SKU → `offer id` фиксируем навсегда.

### 2.2 Теги [Док]

**Уровень магазина:**

| Тег | Обяз. | Примечание |
| --- | --- | --- |
| `yml_catalog@date` | да | Дата генерации |
| `shop` | да | |
| `name`, `company`, `url` | нет | ≤ 255 символов, не публикуются |
| `currencies/currency@id@rate` | да | `UAH` с `rate="1"`; USD/EUR — по своему курсу |
| `categories/category@id` | да | Свои категории. Название ≤ 255. Рекомендуется называть как на Rozetka |
| `category@rz_id` | нет | ID категории Rozetka для **автосвязки**; приоритетнее названия |
| `offers` | да | |

**Уровень товара (`offer`):**

| Тег | Обяз. | Примечание |
| --- | --- | --- |
| `offer@id` | да | Уникальный, латиница и цифры, неизменный. Каждый вариант (цвет, размер, комплектация) — отдельный `offer` |
| `offer@available` | да* | `true` / `false` |
| `stock_quantity` (или `quantity_in_stock`) | **да** | Целое. Без тега товар «немає в наявності». Товар в наличии, пока значение > 0 |
| `price` | да | Целое или дробное; на сайте округляется до гривен |
| `price_old` / `old_price` | нет | Зачёркнутая цена, должна быть > `price` |
| `price_promo` / `promo_price` | нет | Промо-цена для участия в промоакциях; проверка соответствия — ежедневно в 08:00 |
| `currencyId` | да | `UAH` / `USD` / `EUR` |
| `categoryId` | да | ID своей категории из `<categories>` |
| `picture` | да | 1–15 шт., https, без кириллицы, пробелов и `+`, ≤ 1999 символов. Первая — главная |
| `vendor` | да | Бренд. Если бренда нет — `Без бренду` |
| `article` | нет | Артикул (виден в кабинете) |
| `name` / `model` | да | ≤ 255. **Русское** название. Дубли названий в фиде запрещены |
| `name_ua` / `model_ua` | нет | Украинское название; если нет — автоперевод с русского |
| `description` | да | ≤ 50 000, HTML в CDATA. **Русское** описание |
| `description_ua` | нет | Украинское описание |
| `param@name` | да | Характеристики; значение ≤ 500 символов; пустые запрещены |
| `param@paramid`, `param@valueid` | нет | ID характеристики и значения Rozetka для автосвязки. Для ComboBox, List и CheckBox-типов `valueid` обязателен, если указан `paramid` |
| `param/value@lang="uk"\|"ru"` | нет | Двуязычное значение текстовой характеристики |
| `url` | нет | Ссылка на товар на нашем сайте, ≤ 500 |
| `state` | нет | `new` (по умолчанию) / `stock` (уценка) / `used` / `refurbished` |
| `docket`, `docket_ua` | нет | Краткое описание ≤ 255; обязательно для уценки |
| `min_cart_quantity`, `max_cart_quantity` | нет | Мин./макс. количество в корзине |
| `param name="EAN"` | условно | Штрихкод 8–14 символов. Обязателен для ряда категорий, помогает группировке |

\* `available` описан в теге `offer` как признак наличия, но наличие фактически определяет `stock_quantity > 0`. Передаём оба согласованно.

### 2.3 Категории [Док]

- В фиде — **наши** категории. Связь с категориями Rozetka настраивается при модерации или автоматически через `rz_id`. Рекомендуется не смешивать в одной нашей категории товары из разных категорий Rozetka.
- ID категории Rozetka — число после `c` в URL конечной категории. Например, «Дитячі конструктори»: `rozetka.com.ua/ua/building_kits/c97420/` → `rz_id="97420"`. ID найден по поисковой выдаче; сверить с «Довідниками» в кабинете.
- Связку можно сделать и через API: `POST /price-markets/create-bindings-categories`, `GET /price-markets/categories-by-price`. Справочник категорий: `GET /market-categories/search`, `GET /market-categories/get-categories-by-parent`.
- Новую категорию Rozetka создаёт только по заявке в поддержку, это занимает от 2 месяцев. Перенос товара в другую категорию — тоже через поддержку.

**[Вывод]** Для админки нужна таблица соответствия «наша категория (и подкатегория) → `rz_id`». Наши «Конструктори → LEGO» и «Дерев'яні конструктори» могут попасть в одну категорию Rozetka. Тогда в фиде лучше завести отдельные `category id` под каждую пару «наша подкатегория × категория Rozetka».

### 2.4 Характеристики [Док]

- Минимум **3 характеристики** на товар. Названия характеристик — на одном языке.
- Список характеристик и значений по категории доступен в кабинете («Управління товарами» → «Довідники») и **через API**: `GET /v1/market-categories/category-options` (JSON), `GET /market-categories/download-options` (XLS), `GET /items-create/attributes`, `GET /items-create/values`.
- Если характеристики нет в категории Rozetka, она не покажется на сайте. Её можно указать в описании или в параметре «Додаткові характеристики». Новое **значение** (например, новый цвет) добавляется при модерации автоматически.
- Обязательно передавать характеристику, по которой группируются варианты (цвет, размер и т. п.). Правила группировки по категориям — в кабинете, в API — `GET /grouping-service/group-strategy/search`.
- Логистические параметры: вес, высота, ширина, глубина в упаковке, количество мест. На сайте не показываются, но без них Rozetka подставит средние по категории, и часть отделений или почтоматов может стать недоступной.

**[Вывод]** Наш атрибут «возраст» (`6–12 років`) нужно сопоставить с характеристикой возраста в категории Rozetka. Точное название и `paramid` берём из справочника, в этом исследовании они не проверены.

### 2.5 Изображения [Док]

- 1–15 фото; оптимально 3–6. Размер от 400×400 до 4000×4000 px, оптимально 1000×1000. Зум работает от 720×630.
- Форматы JPEG, PNG, GIF, WebP; ≤ 10 МБ; RGB или sRGB.
- Главное фото: товар без упаковки, не обрезан, фон белый, светлый или прозрачный (пастельный однотонный допустим). Без текста и водяных знаков, иначе товар не попадёт в Google Shopping.
- **Запрещены маркетинговые плашки на фото** («хіт», «акція», «безкоштовна доставка» и т. п.). Надписи на фото — только на украинском (английские термины допустимы).
- С 31.01.2027 для Google Shopping нужно минимум 500×500.
- Если сервер картинок ограничивает доступ, надо открыть его для IP Rozetka: `89.184.81.192/27`, `89.184.81.128/26`, `78.27.198.0/24`, `89.184.65.128`, `88.81.226.126`, `78.27.198.189`, `91.210.37.210`, `45.128.216.254`, `45.128.217.251`.

**[Вывод]** Наши бейджи `Хіт` / `Новинка` / `−18%` нельзя «зашивать» в картинки. Их аналог на Rozetka — `price_old` (скидка считается автоматически) и промоакции.

### 2.6 Цены, скидки, промо [Док]

- Цены только в гривнях, без копеек (округляются). Оптовых цен нет.
- Скидка — пара `price` + `price_old`. Чтобы убрать скидку, удаляем `price_old`.
- Промо — `price_promo`. Проверка соответствия требованиям промоакции — ежедневно в 08:00. Можно передавать одновременно с `price_old`: на сайте зачёркнутая цена плюс красная промо-цена.
- Rozetka рекомендует ту же цену, что на нашем сайте. Запрещены только цены «необґрунтовано вищі» за вартість у інших точках збуту; наказание — скрытие товара, ограничение продаж в категории, прекращение сотрудничества ([p214](https://sellerhelp.rozetka.com.ua/p214-price-and-stock.html)). Наценка на размер комиссии — наше обоснование, признание остаётся за Rozetka.
- Резкое изменение цены считается ошибкой: товар уходит во вкладку «Підтвердження ціни» и становится неактивным, пока продавец не подтвердит цену в кабинете. **Пороги в источниках расходятся:** справка говорит «в 3 раза вверх или в 2 раза вниз», описание `PUT /items/mass-update` — «более чем в 1,5 раза вверх или в 2 раза вниз». Отдельно для категорий действуют min/max-диапазоны, вне которых цена «аномальна» (`GET /goods/quarantine`).

### 2.7 Языки (uk/ru) [Док]

- `name` и `description` — русский, `name_ua` и `description_ua` — украинский. Для текстовых параметров — `value lang`.
- Перевод с русского на украинский автоматический. С украинского на русский — **не переводится**.
- Если фид только на украинском, нужно сообщить в поддержку: они выставят фиду статус «украинский» и отключат автоперевод.
- Если в фиде есть обе версии, приоритет у украинской.

**[Вывод]** Наш сайт украиноязычный. Придётся либо вести русские тексты в админке, либо договориться с поддержкой о фиде только на украинском. Как в этом случае заполнять обязательный `<name>` (украинским текстом?) — уточнить у поддержки (см. открытые вопросы).

### 2.8 Варианты и наборы [Док]

- Каждый вариант — отдельный `offer` со своими фото, ценой и характеристиками. Отличие указывается в названии. Rozetka группирует варианты при модерации по параметру группировки.
- Группировку вне правил и разгруппировку делает только поддержка.
- Наборы: название начинается с «Набір/Комплект» и перечисляет состав через «+». Скидка за несколько одинаковых товаров — через комплекты «Разом дешевше» (API: `KitsModule`).

### 2.9 Удаление товара [Док]

- Если убрать товар из фида, он **не исчезает с сайта**: переходит в «немає в наявності» и вкладку «Видалені з прайсу». Чтобы вернуть, достаточно вернуть его в фид с тем же `id`.
- Полностью скрыть товар можно архивацией (кабинет, только активные товары) или через поддержку.
- Автоархивация происходит 1-го числа месяца: товары без наличия 15 месяцев, без просмотров, отзывов и добавлений в «Список бажань». Разархивация — через поддержку.

## 3. Механизмы обновления и частота

### 3.1 Чтение фида [Док]

- Rozetka сама скачивает фид по URL (pull). Стандартный период — **раз в час**. Период видно в `sync_period` у `GET /markets/sources-list` (в примере — `60`).
- **Ручная синхронизация:** кабинет → «Управління прайс-листами» → «Синхронізувати». Не чаще **1 раза в 3 часа**. Недоступна, если автосинхронизация прошла меньше 10 минут назад или фид заблокирован. **API-метода для принудительной синхронизации не найдено.**
- Подключение фида и замена его URL — только через поддержку.
- `GET /markets/sources-list` отдаёт по каждому фиду: `last_sync_ts`, `last_sync_api`, `total_items_count`, `synced_items_count`, `sync_type` (полная или короткая), `availability` (1 — наличие в прайсе, 2 — по наличию, 3 — по остаткам, 4 — по API), `sync_enabled`, `sync_period`, `moderation_type`, `columns_for_sync` и др. Это пригодится для индикатора «Синхронізовано о 09:40» в нашей админке (`docs/admin/design/01-overview.md`, `06-integrations.md`).

### 3.2 Изменения контента требуют модерации [Док]

- Цена, наличие, остаток и мин./макс. корзины из фида применяются после синхронизации **автоматически**.
- Название, описание, фото и характеристики после синхронизации попадают в «На підтвердження» → «Очікує підтвердження». Применяются только после **заявки на модерацию**: вручную или через «Автозаявку», которая по умолчанию срабатывает раз в сутки в 08:00; расписание меняет поддержка.
- Новые товары тоже проходят модерацию. Фиксированных сроков нет. Подключение нового продавца занимает от 2 недель до 2 месяцев.

**[Вывод]** Правка карточки в нашей админке дойдёт до Rozetka не раньше следующей синхронизации (≤ 1 ч) плюс модерация (не меньше суток при автозаявке). В админке нужно честно показывать статус «на модерації Rozetka».

### 3.3 Быстрое обновление цены и остатка через API [Док]

- `PUT /items/mass-update` — массовое изменение по `item_rz_id` (ID товара в Rozetka) полей: `price`, `price_old` (`-1` удаляет), `price_promo` (`-1` удаляет), `stock_quantity`, `min_cart_quantity`, `max_cart_quantity`. Право доступа — `api_items_actions`. Параметр `isIgnoreCheck` (0 или 1) управляет валидацией. Ошибки возвращаются по каждому товару.
- Предусловие (справка p742): у прайс-листа должен быть тип синхронизации **«Особистий кабінет (API)»**. Переключается в кабинете. После этого «актуальною буде вважатися інформація, яку ви вносите в кабінеті». При возврате к типу «Прайс-лист» значения, внесённые через кабинет или API, перезапишутся фидом.
- **[Вывод]** При типе «Особистий кабінет (API)» цена и остаток из XML игнорируются, а контент продолжает обновляться из фида. Документация прямо этого не формулирует — проверить на тестовом товаре.
- **Лимитов** на размер батча и частоту вызовов документация не приводит.
- Нужно соответствие `offer id` ↔ `item_rz_id`: `GET /goods/all?price_offer_id=TM10018` (или `?article=TM-10018`) → поле `id`. Изменённые цены и товары: `GET /goods/prices`, `GET /goods/changes`.

### 3.4 Альтернативы фиду [Док]

- Создание товара через API: `POST /items-create/create`. Массовое редактирование основных данных: `PUT /items-create/mass-update-basic-data` (надо передавать **весь** список параметров; категорию можно менять только у нового товара).
- Импорт и обновление через XLS-шаблон: `/items-file-import/*`.
- Для товаров, созданных в кабинете или таблицей, Rozetka генерирует отдельный «виртуальный» прайс-лист.

**[Вывод]** Теоретически весь каталог можно вести через API без XML. Но это требует маппинга характеристик на ID справочников Rozetka и не избавляет от модерации. Для старта фид проще и стандартнее.

## 4. Возможности API

**База:** `https://api-seller.rozetka.com.ua`. Документация: `https://api-seller.rozetka.com.ua/apidoc/`. Справка также ссылается на `cabinet-seller.rozetka.com.ua/apidoc/`.

**Авторизация [Док]:**

- `POST /sites` с `{"username": "...", "password": "<base64>"}` → `content.access_token`. Дальше заголовок `Authorization: Bearer {token}`.
- Токен продлевается при использовании и истекает после 24 часов простоя.
- В кабинете («Налаштування» → «Безпека API») можно генерировать отдельные API-токены, привязанные к роли: владелец, администратор, контент-менеджер, финансы, обработка заказов. До 10 токенов на менеджера. Неиспользуемый 24 часа токен деактивируется.
- Ответы всегда HTTP 200 с телом `{"success": true|false, "content": ..., "errors": {message, code, details}}`. Ошибки определяются по `success` и кодам (1004 — неверный логин или пароль, 5401 — не авторизован, 6001 — сессия истекла, 3002 — товар заблокирован и т. д.).
- Язык ответа задаётся заголовком `Content-Language: uk|ru`. Для получения ошибок валидации в методах `search` — заголовок `Accept-Validate-Exception`.
- Пагинация: `page`, `pageSize` / `perPage`, в ответе `_meta`.

**Rate limits:** в спецификации и справке не упомянуты (поиск по «limit», «429», «too many» ничего не дал).

## 5. Заказы и синхронизация остатков

### 5.1 Как узнать о новом заказе [Док]

- **API-опрос:** `GET /orders/search?types=4` (новые) или по `created_from` / `changed_from` / `status_updated_from`, с `sort=-id`. По умолчанию метод возвращает группу «В обработке».
- **Вебхуков нет** в официальной спецификации и справке.
- **Push продавцу:** Telegram, Viber/SMS, email (настройки уведомлений). Машиночитаемого колбэка на наш сервер нет.

### 5.2 Обязанности по времени [Док]

- Новый заказ нужно перевести в статус 26 «Опрацьовується менеджером» желательно в течение 2 часов и не позже 24 часов (по графику работы). Иначе Rozetka ставит 7 «Не оброблено продавцем протягом дня», а через 7 дней — «Виконано».
- Заказ в обработке дольше 30 дней автоматически закрывается статусом 87 «Виконано. Минув термін обробки».
- Частые отмены из-за отсутствия товара ухудшают рейтинг и могут привести к **блокировке магазина**.

### 5.4 Как Rozetka сама меняет остаток [Док]

- При оформлении заказа Rozetka вычитает заказанное количество из остатка и не даёт заказать больше доступного. При 0 товар становится «Немає в наявності».
- При **отмене** заказа количество автоматически возвращается в остаток.
- Если остатки идут из XML, следующая синхронизация перезапишет остаток значением из фида. Поэтому продавец «повинен самостійно віднімати замовлену кількість» в своей системе.

### 5.5 Рекомендуемая схема синхронизации [Вывод]

```
           ┌────────────── Сайт «Trio Mio» (источник правды: stock_on_hand, reserved) ──────────────┐
           │                                                                                    │
  XML-фид (контент, раз в час) ──► Rozetka           Воркер «orders-poll» (каждые 1–2 мин)      │
  API mass-update (цена+остаток) ──► Rozetka ◄─────── GET /orders/search?changed_from=…         │
           │                                          → upsert заказа, резерв, PUT статус 26     │
           └──► Prom / Epicentr (их механизмы) ◄───── пересчёт available = on_hand − reserved ──┘
```

1. **Источник синхронизации на Rozetka** — «Особистий кабінет (API)». Фид продолжает нести контент. Цену и остаток пушим через `PUT /items/mass-update`.
2. **Опрос заказов** каждые 1–2 минуты по `changed_from` или `status_updated_from` от последней метки, с запасом перекрытия; дедупликация по `order.id`. Новые заказы (статус 1) — создать заказ в админке, **зарезервировать** количество по `purchase.item_id` → `price_offer_id` → наш SKU, перевести заказ в 26 через API (снимает риск автостатуса 7).
3. **Пересчёт и раздача.** `available = on_hand − reserved` → `mass-update` на Rozetka и аналогичные вызовы на Prom и Epicentr. Пушим **абсолютные значения**, не дельты: Rozetka уже вычла остаток у себя, а абсолютное значение идемпотентно и исправляет расхождения.
4. **Отмены и возвраты** (переход в группу 3 или статусы возврата) — снять резерв или вернуть на склад, снова пушнуть абсолютные остатки. Rozetka вернёт остаток у себя сама, наш пуш просто совпадёт или поправит.
5. **Сверка раз в сутки:** `GET /goods/all` (поля `stock_quantity`, `price`, `sell_status`) против нашей базы; плюс `GET /goods/errors` и `GET /goods/not-valid`.
6. **Окно гонки.** Между продажей на Prom и нашим пушем на Rozetka проходит до одного цикла (секунды–минуты). Для товаров «Закінчується» с малым остатком можно держать страховой буфер (отдавать на маркетплейсы `available − 1`). Это бизнес-решение.
7. **Токен:** отдельный API-токен роли «обработка заказов» для воркера заказов и роли «контент» для товаров. Воркеры работают постоянно, поэтому токен не простаивает 24 часа.

## 7. Открытые вопросы к владельцу бизнеса

1. **Числовые остатки.** В админке сейчас только статусы. Rozetka требует целое число в `stock_quantity`. Будет ли на сайте учёт количества по SKU (и резерв)? Какой порог считать «Закінчується»?
2. **«Очікується»** на Rozetka выглядит как «немає в наявності». Устраивает ли это, или нужен отдельный тег (уточнить у менеджера Rozetka)?
3. **Языки.** Готовы ли вести русские названия и описания, или просим поддержку перевести фид в режим «только украинский»? Если второе — что ставить в обязательный `<name>`?
4. **Бренды.** Для позиций без бренда (TM-10077, TM-10103, TM-10155, TM-10204) — реальный производитель или `Без бренду`? Бренд проходит модерацию и может потребовать документы.
5. **Фото.** Есть ли у нас главные фото на белом фоне без плашек и текста, минимум 1000×1000? Сколько ракурсов на товар?
6. **Цены.** Решено: наценка под комиссию Rozetka по правилу из админки. Правила запрещают только «необґрунтовано вищі» цены, не любую цену выше сайта.
7. **Промо.** Участвуем ли в промоакциях Rozetka (`price_promo`)? Кто в админке решает про скидки по каналам?
8. **Логистика.** Будут ли вес и габариты в упаковке для каждого SKU? Без них часть способов доставки недоступна.
9. **SKU → `offer id`.** Согласны ли на правило «убрать дефис» (`TM-10018` → `TM10018`) навсегда?
10. **Обработка заказов.** Кто подтверждает заказ Rozetka (звонок покупателю — требование площадки): менеджер в нашей админке или в кабинете Rozetka? Нужен ли автоперевод в 26 сразу при получении?
11. **Доставка.** Свои ТТН Новой Почты, RZ Delivery или фулфилмент Rozetka? От этого зависит, кто списывает остаток физически.
12. **Буфер остатков.** Допускаем ли страховой резерв на маркетплейсах для малых остатков?

### Что проверить на живом кабинете (технически)

- Действительно ли при типе «Особистий кабінет (API)» контент продолжает обновляться из XML, а цена и остаток игнорируются.
- Фактические лимиты частоты и размера батча у `PUT /items/mass-update` и `GET /orders/search`.
- Что именно делает `isIgnoreCheck=1`: отключает ли проверку резкого изменения цены.
- Точные названия и ID характеристик возраста, серии и количества деталей в категориях игрушек (через `GET /v1/market-categories/category-options`).
